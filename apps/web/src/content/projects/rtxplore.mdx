**RTXplore** started as my bachelor thesis: a graphics engine that integrates both rasterization and ray tracing.

# What I Built

The goal was to render the same complex scene with both rendering techniques and compare visual quality and performance. This was primarily an educational project: I wanted to understand how both systems really work and what trade‑offs they impose. The engine runs a single scene across two complete pipelines with shared resource management so comparisons are apples‑to‑apples.

The **scene** features:

- Procedural terrain generated with fractal fBm over 2D Simplex noise.
- Water with two animated wave scales: small ripples and large swells.
- A dynamic skybox for image‑based lighting cues.
- Texturing via a dedicated loader, normal mapping and displacement mapping; distance-based tessellation to keep near detail while reducing far‑field cost.

How each **pipeline** handles water and optics:

- **Ray tracing**: large waves are modeled via an Intersection Shader over procedural AABB primitives; reflections and refractions come from recursive rays.
- **Rasterization**: large waves are produced through displacement/tessellation; reflections and refractions use dynamic cube mapping with geometric corrections.
- Both paths render dynamic shadows: shadow rays in RT; **shadow mapping** in rasterization.
- **Frustum culling** to optimize rendering by excluding non-visible objects - of course only in rasterization.

Lighting uses a **Blinn-Phong model** with a **Schlick approximation** for Fresnel, implemented symmetrically across both pipelines for visual parity.

## Architecture highlights

- DirectX 12 on Windows: swapchain, resource views (RTV/DSV/CBV/SRV/UAV), Pipeline State Objects and Root Signatures.
- Acceleration structures: BLAS/TLAS with shader tables for ray tracing (closest-hit/any-hit/miss).
- **Custom math library** as a wrapper over DirectX SIMD types.
- Systems for object generation, texture loading, dynamic cube mapping and shadow mapping.
- Keyboard and mouse controls through a simple input manager.

## Ray Tracing

In ray tracing, the process of achieving visual effects is more straightforward and
natural, based on a technique called recursive ray tracing. When an intersection is reported
to a closest hit shader the reflection and refraction vectors are calculated within
the shader. Rays are then launched into the scene in the directions of these vectors.
These rays return the captured colors, which are then combined with diffuse lighting and
shadowing.

# Ray Tracing vs. Rasterization

In this section, I present a comparative analysis of rasterization and ray tracing by rendering
the same scene using both methods. This analysis explores the differences and
similarities in the visual effects produced by each technique, as well as examines the resources
utilized, such as memory usage and computational load.

## Visual Differences

Although the scene looks geometrically identical in both rasterization and ray tracing,
notable differences emerge in global illumination and texturing details. These differences
arise from the fundamentally different approaches each method uses to handle drawing
to screen and lighting.

- Ray tracing images show **noise** when using 1 spp; rasterization stays clean at similar cost, as can be seen in the image below. A denoiser (e.g., RTDAO) would mitigate it.

### Performance Metrics

I am aware that the two systems are fundamentally different and that direct comparisons are not always fair. But still,
you can see the numbers below as highlights of each system's performance in my specific implementation, and not as
a comparisson of the technologies in general.

- **Rasterization** - I assessed the framerate, which is heavily influenced by the graphics card
  driver and refers to the number of Frames per Second (FPSs) displayed. The tests and
  metrics were obtained using Game Ready Driver version 555.99 for the NVIDIA RTX 4070 graphics card.
  With dynamic cube map updates occurring in every frame, an average
  framerate of 1700 ± 10% FPS was achieved. When the dynamic cube map was updated
  every 0.1 seconds, the framerate increased to 3300 ± 15% FPS.

- **Ray Tracing** - Regarding framerate, I achieved approximately 230 FPS ± 30%. This framerate
  can vary drastically depending on the camera’s position. If the camera is very close to
  an object, the BVH traversal heuristic algorithms can more efficiently find the intersected
  geometry compared to when the camera views the entire scene. This efficiency arises
  because closer objects result in shorter traversal paths within the BVH, reducing the
  computational load. Conversely, viewing the entire scene involves more extensive BVH
  traversal, increasing the rendering time.

### Key Takeaways

- Rasterization wins for throughput and predictable cost; great for live interaction and broad hardware.
- RT wins for correctness of reflection/refraction at grazing angles, edge cases, and multi-bounce paths.
- My engine lets you toggle the pipeline while keeping the same scene and materials, so differences are visible—not theoretical.

# Technical Highlights

In this section I will highligh some of the technical aspects of the engine, such as how I got to generate the terrain, how the
shadow map works, how I implemented the intersection shader for the procedural water and how reflections and refractions are handled in both pipelines.

## Procedural Terrain (Height Map)

- Terrain generated with fractal **fBm** over 2D **Simplex noise** (coherent; deterministic), then scaled to realistic heights.
- Mesh is split into **chunks** with AABBs for **frustum culling**; only visible submeshes are drawn.
- The image below shows the generated height map used for the terrain.

## Water: Small and Large Scale Waves

Tessellation/domain stage computes displaced positions and TBN matrix; pixel stage applies normal/diffuse sampling (terrain uses arrays with height-based blending; water uses uniform color + normal).

## Shadows

- **Shadow mapping** pass with orthographic light camera, depth bias and **PCF** filtering to soften edges.
- In RT path, a **shadow ray** + boolean payload determines occlusion via miss-shader logic.

## Ray-Surface Intersection (Procedural)

Procedural water in RT uses **AABB primitives** and an **Intersection Shader** to compute the exact displaced hit before closest-hit shading.

<ProjectImage
  src={`${imagesPath}/IntersectionShader2.png`}

## Reflections & Refractions — how each pipeline does it

- **Rasterization:** dynamic cube-mapping from six 90° cameras; refraction via env-map + geometric correction.
- **Ray tracing:** recursive rays in closest-hit; colors from reflection/refraction rays are combined with direct light and shadows.

# Future Work

- Implement a denoiser (e.g., RTDAO) to clean up noise in ray-traced images at low samples per pixel.
- Add more complex materials (e.g., metals, translucency) and support for IOR variations.
- Optimize performance further by exploring advanced acceleration structures and ray traversal techniques.
- Add shader hot swapping in debug and shader precompiling in release, for faster iteration times.
- Integrate additional global illumination effects, such as ambient occlusion and soft shadows.
- Explore hybrid rendering techniques that combine the strengths of both rasterization and ray tracing - such as deferred hybrid path tracing.
- Add support for TOML based settings and scene description to make it easier to configure and extend the engine.
